> 本篇在**篇八（无状态化）+ 篇九（6 层安全）**的基础上做高可用：**只加冗余与降级，不改工具定义**。
> `STATELESS` 协议不变，`@Tool` / `@ToolParam` 写法不变——HA 是部署形态的事，不是业务代码的事。
> ⚠️ 本篇示例**未叠加篇九的鉴权/限流/审计**（避免样例过重），生产落地请把两者叠加。

### 本篇跑通的 HA 能力

| 层 | 内容 | 代码位置 |
|---|---|---|
| 水平扩容 | 3 实例 + Nginx 加权轮询 3:2:1，被动健康检查 `max_fails=2 / fail_timeout=10s` | `nginx/nginx.conf` |
| 健康检查 | `/actuator/health` 暴露 health/info，开启 liveness/readiness，供 LB 与探针摘除坏实例 | `application.yml`（management 段） |
| 熔断降级 | Resilience4j：`get_device_status` 慢调用 >1s 计失败，失败率/慢调用率 50% 打开，10s 后半开试探，打开走 fallback | `service/StoreService.java` |
| 软降级 | `get_store_sales` 读 Redis 缓存，命中标注 `来源=缓存`；Redis 挂了降级返回源数据，不报错 | `service/StoreService.java` |
| 状态/规则外置 | 上下文外置 Redis（`store.context.type=redis`），补货规则表外置 `rule:restock-multiplier`，多实例读到同一份 | `store/RedisContextStore.java`、`service/StoreService.java` |
| Redis 高可用 | 1 主 2 从 + 3 哨兵监控 `mymaster`，主库挂了自动故障转移 | `docker-compose.yml`、`redis/sentinel*.conf`、`application-docker.yml` |
| 容器编排 | 一键起 3 实例 + Redis 主从哨兵 + Nginx | `docker-compose.yml`、`Dockerfile` |
| K8s 版 | Deployment 3 副本 + readiness/liveness 探针 + ClusterIP Service（Redis 走集群内单机 Service） | `k8s/*.yaml`、`application-k8s.yml` |

> 四个踩坑点，正文都写了：
> - Nginx 必须显式 `proxy_set_header Host $host`——否则 upstream 名 `mcp_backend` 里的下划线会让 Tomcat 11 回 400
> - 无状态之后若把上下文放本地内存（`store.context.type=memory`），多实例下 `save_context` 在 A、`load_context` 在 B 就读不到，这是 HA 最常见的翻车点
> - 哨兵要写自己的配置文件来持久化状态，宿主机挂载的 `redis/sentinel*.conf` 属主不是容器内的 redis 用户，直接挂到 `/etc/sentinel.conf` 会满屏 `Permission denied`——compose 里改成挂到 `/mnt` 只读、启动时拷进 `/data` 再运行
> - 故障演练要用 `pause` 而不是 `stop`（原因见下方哨兵演练一节）

### 跑起来

```bash
git clone https://gitee.com/ethanliang2016/mcp-in-action.git   # 国内
# git clone https://github.com/ethanliang2016/mcp-in-action.git # 海外
cd mcp-in-action && git checkout v10

cd 10-store-ha
mvn -q package -DskipTests        # 产出 target/store-ha-1.0.0-SNAPSHOT.jar
docker compose build
docker compose up                 # nginx :8080 -> 3× app :8088 + redis 主从哨兵
```

本地单机直连（不进容器，需本机 Redis `localhost:6379`，或改 `store.context.type=memory` 只做对照演示）：

```bash
cd 10-store-ha && mvn spring-boot:run    # 端口 8088
```

### 实测脚本

容器起来后，统一走 Nginx `:8080` 验证完整链路：

```bash
pip install mcp
python verify/ha_check.py poll       # 轮询：连续 save_context，看“处理实例=app-N”是否分散
python verify/ha_check.py normal     # 正常路径：设备状态 / 门店销售应正常返回
python verify/ha_check.py circuit    # 熔断：连续调设备状态，应逐步转“熔断降级”
python verify/ha_check.py sentinel   # 哨兵：主从切换后 save/load_context 仍应成功
```

**故障演练**（模拟下游慢但不报错，触发熔断）：

```bash
HA_DEVICE_LATENCY_MS=5000 docker compose up
# 另开终端：python verify/ha_check.py circuit
```

> 熔断是**每实例各自统计**的（`minimumNumberOfCalls=5`），而 Nginx 按权重把请求摊到 3 个实例上，
> 所以某个实例要攒够 5 次慢调用才会打开。实测 12 次调用里会陆续出现 fallback；想让三个实例都打开就把调用次数加大。

**哨兵演练**（验证 Redis 主库故障转移，实测约 7s 完成）：

```bash
docker compose pause redis-master          # 冻结进程，"主库不可用"但不销毁容器
sleep 12
docker compose exec redis-sentinel-1 redis-cli -p 26379 sentinel get-master-addr-by-name mymaster
python verify/ha_check.py sentinel         # 读写应正常，failover 前写的数据也在
docker compose unpause redis-master        # 原主库回来后会被哨兵降级为副本
```

⚠️ **别用 `docker compose stop redis-master` 做这个演练**：容器一停，Docker 网络里的 DNS 别名就注销了，
而哨兵配置开了 `resolve-hostnames yes`，解析失败会让哨兵进入 **TILT 模式**（自我保护，期间不发起 failover），
于是主库明明已经 `+sdown` 却迟迟不切换。实测 `stop` 的情况下 sdown 被拖到 30s 之后且始终没切换；
换成 `pause`（别名保留、IP 不变）后 5s sdown → 7s 完成 switch-master，全程无 TILT。

### 环境

JDK 21+ / Spring Boot 4.0.x / Spring AI 2.0.1 + Resilience4j 2.2.0 + Redis 7 哨兵 / Nginx，全 mock 数据。

> K8s 清单中的镜像为 `store-ha:local` + `imagePullPolicy: IfNotPresent`，
> 需先在所用集群（minikube / kind 等）的节点侧加载该镜像，或改成自己的镜像地址。
