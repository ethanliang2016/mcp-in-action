### 1. 健康检查（经 Nginx）

```bash
curl.exe -s http://localhost:8080/actuator/health     # http_code=200

 "groups":["liveness","readiness"],"status":"UP"}
```

**结论**：LB 到实例、实例到 Redis（经哨兵）链路都通。`redis` 这一项是后面 K8s/Nginx 摘除实例的依据。

### 2. MCP 握手

```bash
curl.exe -s -X POST http://localhost:8080/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  --data-binary '@verify/_init.json'
```

```json
{"jsonrpc":"2.0","id":1,"result":{
  "protocolVersion":"2025-06-18",
  "capabilities":{"completions":{},"prompts":{...},"resources":{...},"tools":{"listChanged":false}},
  "serverInfo":{"name":"store-ha-mcp-server","version":"1.0.0"}}}
```

> ⚠️ **PowerShell 下别用内联 `-d "{...}"`**：`\` 不是 PowerShell 的转义符，
> 双侧引号会被原样塞进 body，服务端解不出 JSON，返回 `400 {"code":-32600,"message":"Invalid message format"}`。
> 用**单引号**包 JSON，或像上面那样写进文件用 `--data-binary @file`。这个 400 是客户端锅，不是服务的。

### 3. 加权轮询分发

```bash
python verify/ha_check.py poll
```

```
[0] 已保存 key=k0 | 存储=redis(外置共享/哨兵) | 处理实例=app-1
[1] 已保存 key=k1 | 存储=redis(外置共享/哨兵) | 处理实例=app-1
[2] 已保存 key=k2 | 存储=redis(外置共享/哨兵) | 处理实例=app-3
[3] 已保存 key=k3 | 存储=redis(外置共享/哨兵) | 处理实例=app-1
[4] 已保存 key=k4 | 存储=redis(外置共享/哨兵) | 处理实例=app-3
[5] 已保存 key=k5 | 存储=redis(外置共享/哨兵) | 处理实例=app-2
```

**结论**：请求被摊到 3 个实例，`app-1` 出现次数明显最多，符合权重 3:2:1。

### 4. 跨实例读上下文（验证状态真正外置）

```bash
python verify/ha_check.py sentinel
```

```
save: 已保存 key=sentinel_test | 存储=redis(外置共享/哨兵) | 处理实例=app-2
load: 读到 sentinel_test=ok  | 存储=redis(外置共享/哨兵) | 处理实例=app-2
```

单次 `save`/`load` 落到哪个实例是 LB 决定的（多次跑会看到 app-1/app-2/app-3 各种组合，偶尔也落在同一个），
所以这一项不能只看"是否落到不同实例"。更硬的证据是**跨轮次读**：用一段脚本读上一轮由别的实例写入的 key：

```
sentinel_test -> 读到 sentinel_test=ok   | 处理实例=app-1
k0            -> 读到 k0=v0              | 处理实例=app-2     # 上轮 poll 写入
k5            -> 读到 k5=v5              | 处理实例=app-3     # 上轮 poll 写入
```

**结论**：无论请求被摊到哪个实例，都能读到别的实例写的数据 → 上下文确实在 Redis 里，不在本实例内存。
（这是与 `store.context.type=memory` 的关键区别，后者多实例下必然读不到。）

## 三、故障演练

### 1. 熔断降级（下游慢而非报错）

```bash
$env:HA_DEVICE_LATENCY_MS=5000                                   # PowerShell
docker compose up -d --force-recreate store-ha-app-1 store-ha-app-2 store-ha-app-3
# 确认生效
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' 10-store-ha-store-ha-app-1-1 | grep HA_DEVICE
#   -> HA_DEVICE_LATENCY_MS=5000
sleep 30
python verify/ha_check.py circuit
```

结果（12 次连续调用）：

```
[0]..[10] 空调 ac-01 运行中，照明 light-03 运行中      ← 还是正常返回，但每次耗时 5s
[11]      设备状态暂不可用（熔断降级）                  ← fallback 生效
```

实例侧日志佐证：

```
store-ha-app-2-1 | WARN c.ethanliang.mcp.service.StoreService : deviceStatus 熔断已打开，返回 fallback
```

**结论**：慢调用 >1s 计入失败、失败率超 50% 打开、打开后返回降级结果，且**只影响 `get_device_status`，其余工具不受影响**（用 `ha_check.py normal` 抽查 `get_store_sales` 仍正常）。

> ⚠️ 一个容易被误读的点：熔断器是**每个实例各自统计**的（`minimumNumberOfCalls=5`），
> 而 Nginx 按 3:2:1 把请求摊开。12 次调用里某个实例可能只分到 2 次，它的熔断器根本没凑够样本、不会打开。
> 想让三个实例都打开，要加大调用次数；不要因为「只有 1 次 fallback」就判定熔断没生效。

### 2. Redis 哨兵故障转移

**前置：先修掉两个会让演练失败的坑**（见第四节问题 1、2），否则会卡在「主库挂了但不切换」。

```bash
docker compose pause redis-master                                # 冻结进程（保留 DNS 别名与 IP）
sleep 12
docker compose exec -T redis-sentinel-1 redis-cli -p 26379 sentinel get-master-addr-by-name mymaster
#   切换前: redis-master / 6379
#   切换后: 172.19.0.5   / 6379
python verify/ha_check.py sentinel                               # 读写应正常
```

哨兵事件流（实测，约 7 秒完成）：

```
15:59:47.862 # +sdown master mymaster redis-master 6379
15:59:48.986 # +odown master mymaster redis-master 6379 #quorum 3/2
15:59:49.671 # +switch-master mymaster redis-master 6379 172.19.0.5 6379
15:59:54.700 # +sdown slave redis-master:6379 ... @ mymaster 172.19.0.5 6379
```

应用侧表现：**演练期间写入成功、切换前写的数据全在**。

```
save: 已保存 key=sentinel_test | 处理实例=app-2
load: 读到 sentinel_test=ok  | 处理实例=app-2

sentinel_test -> 读到 sentinel_test=ok     # failover 前写入
k0            -> 读到 k0=v0                # failover 前写入
k5            -> 读到 k5=v5                # failover 前写入
```

**恢复**（原主库回来后应被降级为副本）：

```bash
docker compose unpause redis-master
sleep 12
docker compose exec -T redis-master redis-cli role
#   slave / 172.19.0.5 / 6379 / handshake / -1     ← 已是新主的副本
docker compose exec -T redis-sentinel-1 redis-cli -p 26379 sentinel master mymaster
#   ip=172.19.0.5  flags=master  num-slaves=2  config-epoch=1  num-other-sentinels=2
```

**结论**：主库故障 → 自动选主 → 应用无感续写续读 → 原主库回归后自动降级为副本，**无双主、无数据丢失**。

## 四、实测中发现的问题与修复

### 问题 1：哨兵配置不可写（Permission denied）

现象，三个哨兵启动后一直刷：

```
# Could not create tmp config file (Permission denied)
# WARNING: Sentinel was not able to save the new configuration on disk!!!: Permission denied
```

原因：宿主挂载的 `redis/sentinel*.conf` 属主不是容器内的 redis 用户，哨兵无法把状态写回配置文件。

修复：`docker-compose.yml` 里改为**只读挂到 `/mnt`，启动时拷进容器内可写目录 `/data` 再运行**：

```yaml
redis-sentinel-1:
  image: redis:7-alpine
  working_dir: /data
  command: ["sh", "-c", "cp /mnt/sentinel1.conf /data/sentinel.conf && redis-server /data/sentinel.conf --sentinel"]
  volumes:
    - ./redis/sentinel1.conf:/mnt/sentinel1.conf:ro
```

修复后 `Permission denied` 彻底消失。

### 问题 2：用 `stop` 演练时哨兵不切换（TILT 模式）

现象：停掉主库后，`sentinel get-master-addr-by-name mymaster` 一直返回旧的 `redis-master`，始终不 failover。

```
15:55:12.243 # Failed to resolve hostname 'redis-master'
15:55:12.299 # +tilt                       ← 进入自我保护，期间不发起 failover
15:55:42.305 # -tilt
15:55:42.305 # +sdown master mymaster      ← 本该 5s 就标记，被拖到 30s 之后
15:55:45.474 # Failed to resolve hostname 'redis-master'
15:55:45.527 # +tilt                       ← 又被踢回 TILT
```

原因：哨兵配置开了 `sentinel resolve-hostnames yes`；`docker compose stop` 会把容器从 Docker 网络注销，
其 DNS 别名随之失效，哨兵反复解析失败，**进入 TILT 模式（自我保护，不发起 failover）**。

修复方式（二选一）：

| 做法 | 效果 |
|---|---|
| `docker compose pause redis-master` | ✅ 别名与 IP 都保留，5s sdown → 7s 完成 switch-master，无 TILT |
| `docker compose stop redis-master` | ❌ 别名注销 → 反复解析失败 → TILT → 不切换 |

**采用 `pause`**，并把这条差异写进 README 与 release-notes，避免读者照 `stop` 做演练时踩同一个坑。

### 问题 3：镜像里的 JAR 是旧的

现象：`poll` 结果里 `处理实例=8088`（端口）而不是 `app-1`。

排查：`docker inspect` 对比时间戳——镜像 **14:36 UTC** 构建，而 jar **15:17 UTC** 才打好，容器跑的是旧类。

修复：

```bash
mvn -q package -DskipTests
docker compose build
docker compose up -d --force-recreate
```

修复后正常显示实例名。**记住：`up -d --force-recreate` 只重建容器，不重建镜像，两者要配套用。**

### 问题 4（代码级）：两个上下文工具返回的实例标识不一致

`saveContext` 用 `resolveInstance()`（返回 `INSTANCE_ID`/端口），`loadContext` 直接用 `port`，
多实例演示时读操作看不出落在哪个实例。已统一为 `resolveInstance()`。

## 六、PowerShell 终端的三个坑

1. **`curl` 是 `Invoke-WebRequest` 的别名**——必须写 `curl.exe`，否则报缺参数。
2. **内联 JSON 会被转义搞坏**（见第二节第 2 项），改用单引号或 `--data-binary @file`。
3. **管道会破坏中文编码**——`python ... | Select-Object -First 6` 之后中文变乱码；
   检查中文内容时不要接管道，直接输出。

> 上面三条都属于本机终端的影响，与被测系统无关，但排查时很容易误判成服务端 bug（第 2 条我就绕了一圈）。

## 七、附录：数据库连接池耗尽的条件实测

正文第 8 节说「Redis 挂了之后查门店销售穿透到 DB，DB 连接池瞬间打满」。这个结论值得验，因为
**"缓存挂了"和"连接池打满"其实是两个不同的事件**，中间还隔着"并发 × 单次查询耗时 vs 池容量"这道门。

本模块是全 mock 数据、**刻意不带真实数据库**（README 里承诺过），所以这组实验在**模块之外**
另起了一套临时容器做，脚本放在 `verify/db-drill/`，不污染 demo 本身。

### 环境与关键设计

| 项 | 说明 |
|---|---|
| 数据库 | `mysql:8.0`（实测 8.0.46），临时把 `max_connections` 降到 **8** 来模拟有限大小的连接池 |
| 缓存 | `redis:7-alpine` |
| 驱动 | 无。全部通过 `docker exec` 调容器内自带的客户端，宿主机零安装 |

> ⚠️ **必须用没有 `SUPER` / `CONNECTION_ADMIN` 权限的账号压测。**MySQL 给管理员保留了
> 1 个额外连接，root 在连接数打满时照样挤得进去——用 root 跑这组实验会得到"永远打不满"的错误结论。

### 实验 1：快查询（对照组）

12 个并发客户端，抢 8 个连接，查询在 200ms 级完成：

```
退出码分布(0=成功 / 非0=失败):
     12 0
Too many connections 次数:
0
```

**12 个全部成功。**并发数超过池大小不会立刻打满——连接用完马上就还了。

### 实验 2：慢查询（实验组）

同样 12 并发、同样池上限 8，只是把单次查询退化成 4 秒（`SELECT SLEEP(4)`）：

```
退出码分布(0=成功 / 非0=失败):
      8 0
      4 1
Too many connections 次数:
4
```

**8 个成功、4 个直接拿不到连接**，失败数正好等于 12 减池容量 8。

### 实验 3：缓存层的放大倍数

同样 5 次请求，量了一下数据库实际承接多少查询。观察窗内的命中序列：

```
场景1 Redis 正常：请求1 未命中 -> 查 DB ｜ 请求2~5 缓存命中（DB 零查询）
场景2 缓存不可用：请求1~5 全部直连 DB
```

> 服务端 `Questions` 计数器包含了探针自身的语句，绝对值偏高，**看倍数和命中序列即可**：
> 有缓存时 5 次请求只有 1 次落到数据库，缓存一挂变成 5 次全部落到数据库。

### 结论

**Redis 挂了 ≠ DB 连接池打满。**准确的关系是：

- 缓存是**节流阀**——阀一没，DB 承受的压力按倍数放大（本例 5 倍）
- 连接池是否真的耗尽，取决于 **并发数 × 单次查询耗时 > 池容量** 这个不等式是否成立
- 现实中这两件事容易伴随发生（热点 key 集体过期、DB 本来就在报警），所以体感上常被记成
  「Redis 挂 → DB 挂」的单一因果

给读者的可操作结论：**给连接池留出余量，并且给 DB 查询设超时**——只要单次查询不会退化到秒级，
哪怕缓存失效、并发超过池容量，连接也能快速轮转，不至于把整个服务拖成不可用。
